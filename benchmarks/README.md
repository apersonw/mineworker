# benchmarks

回答一个问题：**MineWorker 的吞吐在哪里触顶、为什么触顶。**

```bash
python benchmarks/server.py            # 靶子自检：确认它自己不是瓶颈
python benchmarks/run.py --quick       # 小矩阵，几十秒
python benchmarks/run.py               # 完整矩阵
```

## 两个部件

**`server.py`** —— 被压的靶子。asyncio 实现，可配延迟与 body 大小。
自检用**裸 asyncio 客户端**而不是 httpx：这一步要测的是靶子的极限，
用 httpx 会把客户端自己的连接池上限混进来（实测同一靶子 httpx 只能压到 ~48 并发，
裸 asyncio 能到 512）。

**`run.py`** —— 跑矩阵（线程数 × 下载器 × session × 延迟 × parse 成本），输出 markdown 表。

## 怎么读这张表

| 列 | 含义 |
|---|---|
| **QPS** | 用**服务端计时**（首个请求到达 → 末个完成），不含爬虫启动与 1.5s 结束检测轮询 |
| **理论 QPS** | 线程数 ÷ 延迟。每个线程始终在等响应时的上限 |
| **效率** | 实测 ÷ 理论。远低于 100% = 线程大部分时间没在等网络 |
| **平均在途** | **时间加权**平均并发（服务端观测）。**这是解释吞吐的那个数** |
| **峰值** | 瞬时最大并发。会被一次尖峰骗到，不要用它下结论 |

⚠️ **别看峰值看平均。** 峰值能轻松摸到线程数，让人以为「线程都在途上」；
时间加权平均才揭示线程实际有多少比例在等网络。这两个数在早期版本里差了 6 倍，
而正是这个差值指出了真正的瓶颈。

## ⚠️ 限速会影响这里的数字

benchmark 只打**一个域名**（本地靶子），而 0.7.0 起 `CONCURRENT_REQUESTS_PER_DOMAIN`
默认为 8。所以线程数超过 8 时，平均在途会被压在 8 附近 —— **这不是性能回归，
是限速在起作用**。

实测：4 线程 74 QPS（与限速前持平），32 线程 147 QPS / 平均在途 7.5。

想测框架本身的天花板，先解除限速：

```python
setting.CONCURRENT_REQUESTS_PER_DOMAIN = 0
```

真实爬虫通常跨多个域名，每个域各有各的额度，不会像这里一样撞上同一个上限。

## 长跑内存画像（soak.py）

```bash
python benchmarks/soak.py --mode threads          # RSS vs 线程数（一次性开销）
python benchmarks/soak.py --mode time --seconds 600   # RSS vs 时间（泄漏检测）
```

**两个问题必须分开测**：随线程数增长是正常的一次性开销；**只有固定线程数下随时间
持续上涨才是泄漏**。

### 实测结论（2026-09，0.7.0）

**RSS vs 线程数**（每个配置一个干净子进程）：

| 线程数 | 4 | 16 | 32 | 64 | 128 |
|---|---:|---:|---:|---:|---:|
| 增量 | +9MB | +10MB | +12MB | +14MB | +16MB |

4→128 线程（32 倍）只多 7MB，边际成本约 **0.05MB/线程**。

**RSS vs 时间**（16 线程，600s，275 轮 × 400 请求 ≈ 11 万请求）：

| | 斜率 |
|---|---:|
| 前半程 | +14.97 MB/分钟 |
| 后半程 | +2.96 MB/分钟 |
| **最后 1/4** | **+0.22 MB/分钟** |

RSS 在 ~127MB 收敛。**没有泄漏** —— 前期增长是分配器 arena 与各类缓存预热。

### roadmap 里那个「RSS 65→144MB」是假象

那组数字来自两件事叠加，都不是泄漏：

1. **`ru_maxrss` 是峰值、只增不减** —— 当时整个矩阵跑在**同一个进程**里，
   后面的配置继承了前面的峰值。所以 soak.py 用 `ps` 取**当前** RSS，
   且 `--mode threads` 给每个配置开干净子进程
2. **SSL context 未缓存** —— 那时每个请求新建 `httpx.Client()`，各自持有一份 CA 库。
   0.6.0 修掉后内存也顺带大降

### 判据为什么看「最后 1/4」

总斜率会误判：分配器 arena 增长和缓存预热让曲线前重后轻，那是**收敛**不是泄漏。
中段的台阶又会把「后半程斜率」拉高。最后 1/4 才最能分开两者 ——
泄漏在那一段仍会稳定上涨，收敛则压平。

⚠️ **别开 `--trace` 测泄漏**：`tracemalloc` 为每个分配点保存 10 层栈帧，
它自己的开销会随运行增长，把仪器的开销读成被测对象的泄漏。
`--trace` 只在确认有泄漏、需要归因时才用。

## 方法论上踩过的坑

1. **靶子自检用错客户端** —— 一开始用 httpx 自检，得出「靶子只能扛 48 并发」，
   差点据此下调整个矩阵。换裸 asyncio 才发现是 httpx 的上限，靶子能到 512。
2. **wall clock 含固定开销** —— `DONE_CHECK_TIMES × DONE_CHECK_INTERVAL` = 1.5s
   的结束检测在小样本下能淹没真实吞吐。改用服务端计时。
3. **峰值 ≠ 平均** —— 见上。
4. **配置项可能是死的** —— `setting.USE_SESSION` 框架从没读过，只有
   `Request(use_session=)` 生效。benchmark 里 session ✓/✗ 两行数字一模一样才暴露出来。
   **矩阵里两个维度给出完全相同的数字时，先怀疑维度没接上，别急着解释。**

结论见 [docs/async-kernel.md](../docs/async-kernel.md#实测2026-09)。
